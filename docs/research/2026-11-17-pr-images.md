# PR images: getting screenshots and video into pull requests

Date: 2026-11-17

Question: should this repository have a skill that gets images (screenshots,
GIFs, short videos) into pull request bodies and comments, and what should it
say? The user suggested looking at Theo Browne's skills.

Our `pr-description` already ranks screenshots as the strongest evidence for a
visual change (`SKILL.md` §2 item 2) and says to redact images "before upload",
but never says how an agent uploads one. `babysit-pr` and `ship-it` say nothing
about images. That gap is the subject here.

## Bottom line

1. **The upload problem is solved upstream.** GitHub CLI 2.99.0 (2026-09-01)
   added a built-in `--attach '<file>#<alt>'` flag to `gh pr create`, `gh pr
   edit`, `gh pr comment`, `gh issue create`, and `gh issue comment`. It posts
   to the same `uploads.github.com/user-attachments/assets` endpoint the web
   uploader uses, rewrites matching Markdown references in the body to the
   uploaded URL, and appends unreferenced files. Before that, every skill in
   this space worked around "GitHub has no upload API" with browser automation,
   session cookies, scratch repos, or release assets. Those workarounds are now
   obsolete for the common case.
2. **Theo's `tstack` has no image mechanism.** It says "Attach screenshots to
   the PR when they help and you have a way to upload them" (`full-send`) and
   "Screenshots and videos help as well, when you have a way to upload them"
   (`babysit-pr`), and leaves the "way" to the harness (T3 Code). Its useful
   influence is elsewhere: proof is something you observed yourself, and
   screenshots are only worth it when they help.
3. **The two strongest prior-art skills both use `gh --attach`:** Every's
   `ce-commit-push-pr` (`references/visual-evidence.md`,
   `references/apply-and-handoff.md`) and Sentry's `pr-screenshots`. They agree
   on almost everything and supply most of the content a skill needs.
4. **`gh --attach` has sharp edges that none of the sources fully state**
   (verified in the gh source below): it needs write access to the *base*
   repository, so fork PRs to repos you cannot push to fail; it does not work
   on GitHub Enterprise Server; uploads cannot be deleted; and path resolution
   changed in 2.103.0 in a way that breaks Every's recipe on 2.99–2.102.
5. **Recommendation:** add a small `pr-images` skill that owns capture
   → check → upload → refresh for PRs, issues, and comments, and have
   `pr-description` hand image evidence to it. See
   [Recommendation](#recommendation).

## How `gh --attach` actually behaves

Read from [`cli/cli`](https://github.com/cli/cli) at `0536d5e` (main,
2026-11-16) and the release tags named below, package
`internal/attachments` (`doc.go`, `flags.go`, `attach.go`, `client.go`,
`userasset.go`, `references.go`) and the command files under `pkg/cmd/pr` and
`pkg/cmd/issue`.

| Behavior | Detail | Source |
| --- | --- | --- |
| Availability | Present on `pr create`, `pr edit`, `pr comment`, `issue create`, `issue comment` from **v2.99.0 (2026-09-01)**; absent in v2.98.0. Also wired into `issue edit` and `issue artifact` on main. | `pkg/cmd/*` at each tag |
| Argument form | `--attach '<file>#<alt text>'`, repeatable, max **50** per command. An existing path wins over the `#` split, so `#` in filenames works. Stdin (`-`) and duplicate files (same inode) are refused. | `flags.go` |
| File types | png, jpg/jpeg, gif, webp, svg; mp4, mov, webm. Images ≤ 10 MB, video ≤ 100 MB client-side (the server enforces the plan limit: 10 MB video on free plans). | `userasset.go`; [GitHub docs](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files) |
| Rewriting | `![alt](./file)` and `[text](./file)` are repointed; reference-style links are rewritten at the definition; paths inside code fences or inline code are left alone. A video alone in a paragraph becomes a bare URL (renders as a player). **HTML `<img src>` is not rewritten.** | `references.go`; Sentry `pr-screenshots` Step 5 |
| Unreferenced files | Appended to the end of the body as `![alt](url)` (a bare URL for video). With no body flag, `gh pr edit --attach` keeps the existing body and appends. | `attach.go`; `pr create --help` |
| Path resolution | **v2.99–v2.102:** a reference resolves against the working directory only. **v2.103.0+ (2026-10-21):** against the `--body-file`'s directory first, then the working directory. | `attach.go` (`markdownDir` first appears in v2.103.0) |
| Partial failure | Uploads in order and stops at the first failure. If ≥ 1 file uploaded, the PR/comment is **still written** with the successes, the rest stay as local paths, and gh exits non-zero while still printing the URL. Zero uploads → nothing is written. | `doc.go`, `attach.go`, `pr create --help` |
| Permanence | "An upload cannot be undone and there is no endpoint to delete one." Removing the image from the body does not delete the file. | `attach.go` comments; Sentry Step 5 |
| Permission | Needs ADMIN, MAINTAIN, or WRITE on the target repository; the endpoint returns 404 for READ/TRIAGE and gh rewords that. For `pr create` the target is the **base** repository. GitHub App installation tokens have no `viewerPermission`, so gh defers to the endpoint, which "accepts tokens from only some GitHub Apps". | `client.go`; `pkg/cmd/pr/create/create.go` |
| Host | Refused on GitHub Enterprise Server; works on github.com and ghe.com. | `client.go` `checkHost` |
| Ordering | gh builds the uploader before any prompt and uploads after every prompt, so a cancelled editor never strands an upload. `--web` and `--dry-run` reject `--attach`. | `doc.go`, `create.go` |
| Visibility | In private and internal repositories "only people with access to the repository can view the uploaded files." | GitHub docs |

Consequences a skill must state:

- **Never re-run `gh pr create` after a non-zero exit with `--attach`.** The PR
  may already exist. Read it back (`gh pr view <url> --json body`) and repair
  leftover local paths. Every says this; Sentry does not.
- **Version-proof path handling.** Every's recipe puts the body file in the
  images directory and references `./name.png`. On gh 2.99–2.102 that
  reference resolves against the working directory, does not match, and the
  image is appended while the broken `./name.png` stays in the table. The
  portable form is to run gh from the images directory (or write references
  with the same relative path passed to `--attach`, from the same working
  directory).
- **Fork PRs.** A contributor without write access to the upstream repository
  cannot attach on `gh pr create`. The fallback is to open the PR without
  images and either ask the human to drag the files into the web editor or
  link to where they live.
- **Upload is publication.** Because uploads are permanent, the privacy check
  (credentials, tokens, personal data, internal hostnames) happens *before*
  `--attach`, on every image, by looking at it.

## Upload mechanisms compared

| Mechanism | Who uses it | Works on private repos | Pollutes repo/releases | Credential risk | Verdict |
| --- | --- | --- | --- | --- | --- |
| `gh --attach` (2.99+) | Every, Sentry, mitodl/agent-kit PR 574, MuhtasimM/agent-skills PR 5 | Yes, viewers need repo access | No | Normal `gh` token | **Default** |
| Human drags files into the web editor | Fallback in Every/mitodl for old gh | Yes | No | None | Fallback when gh is too old, the repo is a fork, or the host is GHES |
| Browser automation of the web uploader (Playwright/Chrome MCP) | `tonkotsuboy/github-upload-image-to-pr`, `napkin/pr-screenshots` | Yes | No | Drives a logged-in browser | Superseded; Sentry explicitly forbids "upload through the browser's comment box" |
| Session-cookie POST to `user-attachments` | `gh-attach`, `gh-image` community skills | Yes | No | **Needs the `user_session` cookie** | Reject: handles a login credential for something gh now does with its token |
| Commit images to the PR branch or an orphan branch, embed raw URLs | testdouble/han `work-items-to-issues` (`.github/issue-assets/…`), scratch-repo skills | Raw URLs need repo access; not verified for every viewer | Yes: branch or diff noise, permanent history | Normal | Only where a team deliberately keeps images in the repo (han's planning assets) |
| PR-scoped prerelease assets | `toqoz/config` `github-pr-images` | Release assets on private repos need auth | Yes: a release per PR | Normal | Reject: release noise; only advantage (pre-2.99 scriptability) is gone |
| External bucket (S3 etc.) | gstack TODO "Visual verification with screenshots in PR body … Needs S3 upload" (not built) | Depends on bucket ACL | No | Bucket credentials | Only when project instructions name a destination |

Every's rule for project-named destinations is the right generalization: when
project instructions say where PR screenshots go, use that; otherwise check
that the command's `--help` lists `--attach` **before capturing anything**.

## Environment check

This cloud session has gh 2.89.0 and reaches GitHub through the GitHub MCP
server, which has no attachment tool. Neither path can upload an image here.
The skill must therefore detect capability (`gh pr create --help` lists
`--attach`, and `gh auth status` succeeds) and degrade honestly: keep the
images out of the repository, say in the PR body in one line that screenshots
were captured but not uploaded and why, and hand the files to the user.

## Recommendation

Add **`pr-images`** under `skills/engineering/`, model-invoked, as the single
owner of images on PRs, issues, and their comments. Keep it short; most of the
content is the rules above.

1. **Gate.** Capture only for a material visual claim. Text output goes in a
   code block. Follow project instructions on whether running the app or
   taking screenshots needs permission, and on where images go.
2. **Preconditions, checked before capture.** A delivery path (project-named
   destination, or `--help` lists `--attach` and `gh auth status` passes and
   the token can write to the base repository); a browser or tool that writes
   image files; the app runnable at the changed route without new setup.
3. **Capture.** Real build; before from an existing capture or a deployed
   base, never faked; same route, viewport, data, and size per pair; stills
   by default; images in a new temp directory outside the repository.
4. **Check.** Look at every image. Retake rather than blur or crop anything
   with credentials, tokens, personal data, or internal hostnames. Uploads are
   permanent.
5. **Upload.** Markdown tables; run gh from the images directory so
   references and `--attach` paths match on every gh version; one `--attach`
   per image with alt text; on non-zero exit, never re-run create: read the
   body back and repair local paths.
6. **Refresh.** When later commits change what an image shows, retake the
   affected pairs and edit the body, preserving user edits.
7. **Degrade.** No delivery path → no upload, one honest line in the body,
   files handed to the user.

Then shrink `pr-description` §2 item 2 to a pointer ("for screenshots, use
`pr-images`") and add the refresh hand-off to `babysit-pr`. Evals should cover:
a non-visual change (no capture), gh < 2.99 (degrade), a fork PR (degrade), a
partial upload failure (no second create), and an image containing a token
(retake, do not upload).

The alternative is a `references/images.md` inside `pr-description`, as Every
does. That is less to maintain but misses image work that is not a
description: review replies, issue reports, and `babysit-pr` refreshes. Sentry
splitting `pr-screenshots` out of `pr-writer` is the closer match to this
repository's one-owner-per-outcome layout.
