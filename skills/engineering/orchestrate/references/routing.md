# Routing reference

Load this reference when choosing root-only work, delegation, a role, a model tier, or concurrency. It is a decision aid; the active host reference and native tool schema remain authoritative.

## Route by difficulty and verifiability

| Work shape | Route | Model guidance | Evidence of completion |
| --- | --- | --- | --- |
| Small localized edit or lookup | Root | Keep the current root model | Focused diff or direct evidence |
| Narrow mapping, extraction, reproduction, or mechanical check | One cheap native role | Use the least expensive configured role that can meet the check | Paths, symbols, exact command and result |
| Bounded implementation | One owned native worker | Economical routine tier when acceptance is clear; stronger configured tier when ambiguity or impact requires it | Diff plus behavior checks |
| Difficult diagnosis or current external fact | Native researcher/diagnostician | Escalate within the active host only when the evidence need warrants it | Reproduction or authoritative evidence |
| Security, concurrency, compatibility, or material regression review | Independent native reviewer | Stronger configured tier when risk justifies it | Findings tied to the integrated diff |

Difficulty includes ambiguity, dependency breadth, and failure impact. Verifiability includes how directly a result can be checked. High verifiability supports a cheaper role; high ambiguity or consequence supports a stronger role. This is a routing hypothesis, not a claim that model families are universally ranked.

## Dispatch gate

Delegate only a slice with one observable outcome, explicit ownership, available inputs, and a checkable acceptance condition. Keep dependent work behind its prerequisites. Dispatch independent ready slices together, with at most two concurrent workers by default; expand only when separate ownership, capacity, and verification are explicit, and never exceed the active host/profile concurrency cap. A native dispatch must actually succeed before the root treats the slice as delegated.

If a user names an exact model, treat it as a capability requirement: verify that the active native catalog and role permit it. If the user expresses an economical or stronger qualitative preference, a supported configured equivalent can satisfy it when recorded as such. A requested model is never evidence of an observed model. Preserve the root model, role locks, permissions, and existing profiles.

## Compact contract

```text
objective → inputs → owned files → prerequisites → acceptance check
→ native role/model/effort request → tool permissions → retry/return bound
```

The root decides architecture and dependency order. Workers report evidence and stay inside the contract. When no suitable native role exists, return a precise capability gap or take only authorized root work that does not claim the missing delegation.
